# Canaan K230D (VeriSilicon ISP8000)

Status: `styx-k230isp` is written, untested on board. There is no K230 on the bench. The
register map, the parameter builder, the statistics decoder and the device layer are written
and unit-tested against a fake register file (`cargo test -p styx-k230isp --all-features`,
also run under qemu for riscv64). Nothing has touched the hardware.

## Why Styx can drive the ISP itself

The K230D's camera path is a VeriSilicon ISP8000, whose register layout comes from the
Dream Chip MRV block that NXP also licensed. The vendor SDK drives it through a misc device,
`/dev/vvcam-isp.0`, with a register read and write interface and a register-window mmap.
Canaan's 3A runs in user space, as Rockchip's `rkaiq` does on the RK35 parts. Styx writes its
own 3A's parameters and reads its statistics, as it does on the PiSP and on the Rockchip ISPs.
The crate talks to this device only; it does not depend on the vendor kernel's other drivers.

### Block map

The block bases come from the struct's gap arithmetic in `mrv_all_regs.h`; the table is the
brief's, with the AWB measurement block added (the brief had no entry for it):

| Block | Offset | Block | Offset |
|---|---|---|---|
| ISP core | `0x400` | Histogram | `0x2400` |
| Main resizer (MRSZ) | `0xC00` | AE | `0x2600` |
| Self resizer (SRSZ) | `0x1000` | BLS | `0x2700` |
| MI | `0x1400` | DPF | `0x2800` |
| AFM | `0x2000` | DPCC | `0x2900` |
| LSC | `0x2200` | WDR | `0x2A00` |
| | | **AWB measurement** (added) | **`0x2C00`** |
| | | 3DNR | `0x3700` |
| | | EE | `0x3900` |

Cross-check: rkisp1's V10 layout (`rkisp1-regs.h`) puts the ISP core at `0x400`, the AWB
gain of green at `+0x138`, the AWB mean at `+0x144`, the colour matrix at `+0x170`, the CT
offsets at `+0x248`, the gamma points at `+0x1F8`, the histogram bins at the block's
`+0x14` and the AE means at `+0x14`. Those are the offsets the crate uses.

rkisp1 is not the same device, though: its B gain is 14 bits (`AWB_GAIN_B_SET` masks `0x3fff`)
where the MRV field is 10. The fixed-point formats below are the MRV headers' own, not rkisp1's.

## The device

`/dev/vvcam-isp.0`, the vendor driver's misc device (`vvcam_isp_driver.c`, `MISC_DYNAMIC_MINOR`).
The ioctl magic is `'v'`:

| Request | `_IOC` | Argument |
|---|---|---|
| `VVCAM_ISP_RESET` | `0x40047601` (`_IOW`, 4) | a `u32` reset value |
| `VVCAM_ISP_READ_REG` | `0xC0087602` (`_IOWR`, 8) | `vvcam_isp_reg_t { u32 addr; u32 value; }` |
| `VVCAM_ISP_WRITE_REG` | `0x40087603` (`_IOW`, 8) | `vvcam_isp_reg_t` |
| `VVCAM_ISP_CLOSE_IRQ` | `0x40047607` (`_IOW`, 4) | a `u32` (not used) |
| `VVCAM_ISP_FE_START` | `0x40107608` (`_IOW`, 16) | `isp_fe_buffer_t` (not used) |

The driver reads and writes `base + addr` with no range check, so the crate's addresses are
the register window's offsets. The ioctl numbers are checked against their `_IOC` encoding in
the tests. The driver also has an `mmap` of the window (`vvcam_isp_mmap`); the crate does not
use it, since a few hundred register writes a frame are cheap through the ioctl.

## What the crate covers

- `regs`: the block bases, register offsets, and the field masks and shifts the builder and
  the decoder use.
- `Params`: one frame's 3A settings as an ordered list of `(addr, value)` writes:
  - `measure(w, h)`: the AE grid (5x5 blocks of 8-bit luma means, `isp_exp_*`), the histogram
    over the same blocks (16 bins, Y mode), the AWB window (RGB measurement mode);
  - `black_level([R, Gr, Gb, B])`: fixed levels, 13-bit signed;
  - `white_balance([r, g, b])`: 10-bit gains with 8 fractional bits (`100h = 1`), so at most
    3.996;
  - `colour_matrix(m, offsets)`: 9 coefficients row-major, 9-bit signed with 7 fractional
    bits (`080h = 1`), and 12-bit signed offsets;
  - `gamma(curve)`: 17 points of 10 bits over 16 equal segments, the step between points kept
    in the 10-bit signed delta, output enabled in `isp_ctrl`;
  - `lens_shading(w, h, grid, [r, g, b])`: an indirect table of 153 words per colour (two
    12-bit samples to a word), 8x8 sectors, the sector sizes and gradients.

  `Params::apply` writes the list through any `RegisterAccess`, then ORs the control bits into
  `isp_ctrl` (read-modify-write) and sets the vsync shadow update (`ISP_GEN_CFG_UPD`).
- `stats`: `read_raw` (25 AE means, 16 histogram bins, the AWB means and count: 43 reads) and
  `statistics` into `styx_algo::Statistics`: the AE grid as the 5x5 luma grid, the AWB
  white-pixel means as a 1x1 colour grid, the histogram over its 16 bins. The raw blocks are
  taken to measure before white balance and lens shading.
- `device` (feature `device`, Linux): `IspDevice::open`, the register reads and writes, `reset`,
  `statistics`.

The statistics output is `styx_algo::Statistics`, as rkisp's is. The builder takes plain `f32`
and `f64` values, as rkisp's does.

## What is a guess

Each of these is a named constant or a documented choice in the code. None has been checked on
a K230.

1. **Gamma-out position, `0x1F8`.** The struct and rkisp1's V10 layout agree; `mrv_all_bits.h`
   says `0x3F0 + n*4` (absolute `0x7F0` in the TSV). Read the reset state of the array or
   write a ramp and read it back.
2. **LSC table layout.** 153 words per colour and bank, two 12-bit samples to a word, 17 rows
   of nine words. The vertices are taken as the top-left 9 x 9 of the 17 x 18 samples, the rest
   at unity. The bank and set selection (`isp_lsc_table_sel`) is left at set 0.
3. **LSC sector sizes** are in pixels, summing to the frame width (rkisp uses Bayer quads). The
   gradients are `32768 / size`, clamped to the 12-bit field. The field widths (10 bits for
   sizes, 12 for gradients and samples) are the masks; how the hardware uses them is not stated.
4. **Colour matrix order**: row-major (output row, input column). The header names the
   coefficients 0 to 8 without saying which is which.
5. **Colour offsets** go to the cross-talk offset registers (`isp_ct_offset_*`), since the
   headers have no separate colour-matrix offset.
6. **Black level Bayer positions.** The headers do not name the A to D positions. The builder
   assumes an RGGB mosaic read in order: A = red, B = green on a red line, C = green on a blue
   line, D = blue.
7. **Histogram step size 3.** The header says 0 to 2 are not allowed, so the smallest sampled
   pixel is every third. The sub-window weights are all one (the mask positions are stated; the
   value is the builder's choice).
8. **AE luma formula**: `(R + G + B) x 85 / 256` (the header's bit-31 mode). The 3A's luma is
   Rec.601; the difference is a calibration matter.
9. **AWB window size field.** The window offsets are 13 bits (`0x1FFF`, the mask of the core's
   AWB offsets); the size field's width is not in the headers. The builder writes the frame
   size (up to 1280 wide on this sensor) and assumes it holds.
10. **AWB gain zero.** The rkisp driver refuses a zero gain; the K230's behaviour is unknown.
    The builder writes a zero gain as 1/256, as `styx-rkisp` does.
11. **Measurement timing.** The raw blocks are taken to measure before white balance and lens
    shading (`before_wb`, `before_lsc`).
12. **Table writes while the correction is live.** The builder writes the tables, then sizes and
    gradients, then `LSC_EN`, all in one shadow update. Whether the hardware latches the tables
    at the next frame, as the registers' shadowing suggests, is to be confirmed.
13. **CC always on.** The headers show no enable bit for the colour matrix; the builder assumes
    it runs.

## What the headers do not state, and the gap

- **K230-only blocks.** The front end (`ISP_FE_CTL` at `0x3D60`, its DMA and interrupt
  registers, from `vvcam_isp_driver.c` and `vvcam_isp_hal.h`) and the FUSA blocks (the
  `VVCAM_EID_FUSA_*` events of `vvcam_isp.h`) have no field layouts in the sources here. The
  MI extensions the K230 adds (`MIV2_MIS` at `0x16D0`, `MI_MIS_HDR1` at `0x72C8`, `RDCD_MI_MIS` at
  `0x80C0`) are likewise left out. The front end and the FUSA blocks are needed for the sensor
  path, so the K230's capture is not complete on this crate alone.
- **The bit positions of some fields** the masks do not give (the update strobes are from the
  masks, but e.g. the AWB window size).
- **Blocks outside the 3A's set** (WDR, the denoising and edge filters, the defective-pixel
  correction): block bases only, no fields.

## Board smoke checks

Cheap reads that confirm the map before any parameters are written, from the reset values of
`mrv_all_bits.h`:

- `ISP + 0x138` (AWB gain green) reads `0x01000100`; `ISP + 0x13C` (red and blue) the same.
- `ISP + 0x248` to `0x250` (CT offsets) read zero.
- `ISP + 0x1F4` (gamma mode) reads zero after reset: the logarithmic segmentation.
- Write a known gain to `ISP + 0x13C`, read it back, and see the next frame's AWB means move:
  that confirms the shadow update.

## Next steps with a board

   an idle ISP.
2. Build the write list for a flat grey frame (black level, unity gains, identity matrix,
   linear gamma) and apply it. Confirm the frame's AWB means and AE grid come back sane.
3. Resolve the guesses 1 to 4 and 12 by reading back what was written: the gamma position first
   (a ramp), then the LSC table (a known shading: a centre-weighted gain, checked by the
   sensor's brightness across the frame).
4. Wire the frame path (the sensor, the ISP's output, and the front end, whose layout is still
   to be written) through the 3A loop, and report the first frame's timings.
5. Replace the guessed `before_wb` and `before_lsc` with the measured positions.
