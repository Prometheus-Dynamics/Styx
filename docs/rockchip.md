# Rockchip (RK3588 / RK3588S, RK3562, RV1106)

Status: the capture path is written end to end against the vendor driver's uAPI; nothing has
run on an RK3588 yet (no board on the bench). The RK3566 / RK3568 path (ISP21) is written and
unit-tested, not run on a board either: see the RK3566 section below. The ISP32 of the RK3562 and the RV1106 is
written, untested on board too: see [RK3562 and RV1106](#rk3562-and-rv1106-isp32-and-isp32-lite-written-untested-on-board).
The NEON software ISP already runs on any Rockchip ARM board.

## Why Styx can drive the ISP itself

- **Mainline Linux:** the `rkcif` capture driver landed in 6.19 (PX30, RK3568), with RK3588
  capture following. The RK35-generation ISPs (ISP21 in RK3566/68, ISP30 in RK3588(S), the
  RK3576's) have no mainline driver; a from-scratch `rkisp2` is planned upstream.
- **Rockchip's BSP kernel (5.10 / 6.1):** the `rkisp` driver is GPL source, and its parameter
  and statistics buffers are defined in uAPI headers licensed
  `(GPL-2.0+ WITH Linux-syscall-note) OR MIT` (`rk-isp3-config.h` and the `rk-isp21` /
  `rk-isp2` headers it includes). A parameter buffer per frame, a statistics buffer back: the
  same pattern as the PiSP. Rockchip's own 3A (`rkaiq`, partly prebuilt) is not needed:
  Styx's 3A (`styx-algo`) writes the parameters, as it does on the Pi.
- A product on this path runs the vendor kernel until `rkisp2` lands; the parameter and
  statistics backend then follows the mainline interface.

## styx-rkisp

- `uapi`: the ISP21 and ISP30 layouts, generated by `scripts/rkisp-bindgen.sh` from the
  headers in `crates/rkisp/headers` (`uapi::isp21`, `uapi::isp3x`); their sizes (10475-byte
  and 10921-byte parameters, 13700-byte and 16172-byte statistics) and the offsets of the
  blocks used are checked against the C compiler's at compile time. The module bits of
  `module_ens` are written out by hand (`uapi::module`).
- `Params`: one frame's parameters for a `Generation` (`Isp21` or `Isp30`): the statistics
  Styx reads (`measure`: the big raw AE block's 15x15 zone means, the big raw histogram of
  luma), black level, white balance gains, lens shading (the tuning's table resampled to the
  vertices of the generation's sectors: 16x16 on ISP30, 8x8 on ISP21), colour matrix, output
  gamma. The builder's fields the two generations share are written once.
- `statistics`: a statistics buffer of a `Generation` into `styx_algo::Statistics` (colour
  zones and histogram, before white balance and lens shading).

The fixed-point formats the headers do not state are named constants taken from how
Rockchip's 3A fills the same fields, to be confirmed on the device (the ISP21 values are the
same constants: the structures they fill are shared between the generations): white balance gains with 8
fractional bits (`GAIN_ONE`), matrix coefficients with 7 (`CCM_ONE`), 12-bit gamma output
(`GAMMA_OUT_MAX`), lens shading gains with 10 (`LSC_ONE`, 12-bit samples; the sectors
sized over the Bayer quads, half the frame), AE zone means of 10 bits for red and blue and 12 for green (`AE_RB_FULL`,
`AE_G_FULL`).

## The capture path

```text
sensor ─► rkcif ─► rkisp-isp-subdev ─► rkisp-statistics ─► styx_pipeline::rkisp::statistics ─► 3A
                       ▲     └─► rkisp_mainpath (NV12) ─► the capture's frames
                       └──── rkisp-input-params ◄── styx_pipeline::rkisp::params ◄── 3A
```

- `styx_rkisp::device` (feature `device`): `find_isps` lists the media devices with an
  `rkisp-isp-subdev`; `IspDevice::open` enables the links from whatever feeds the ISP's sink
  pad (checking its format against the mode), the parameter node, the main path and the
  statistics node, sets the pad and node formats (`RK1P` / `RK1S` meta, NV12 on the main path)
  and allocates MMAP buffers; parameter buffers are reclaimed as the driver returns them.
- `styx_pipeline::rkisp`: ISP settings to a parameter buffer (black level on 12 bits, white
  balance times digital gain, lens shading, colour matrix, gamma) and a statistics buffer to the 3A input.
- `styx_pipeline::device::RkispPipeline`: the camera's sensor side only
  (`configure_external` / `start_external`, the main path's node for frame timing); per frame,
  statistics through the algorithms, their sensor request to the control schedule, their
  settings into the next parameter buffer, then the main path's frame.
- The `styx` crate picks it for a processed native capture when an ISP is present
  (`isp_kind`, `isp=rkisp`; `STYX_NATIVE_ISP=software` forces the software ISP). It offers
  NV12 modes; the worker copies each frame out of the driver's buffer into a recycled heap
  buffer (handing out dma-bufs comes after the path has run on a board). No crops, regions or
  second output yet: the planner reports a region unmet.

## RK3566 / RK3568 (ISP21): written, untested on board

Status: written, untested on board. The ISP21 layouts, the parameter builder and the
statistics decode are written against the vendor driver's source (`drivers/media/platform/
rockchip/isp` in `develop-5.10`: `isp_params_v2x.c`, `isp_params_v21.c`, `isp_stats_v21.c`) and
unit-tested against fabricated buffers (`cargo test -p styx-rkisp`). Nothing has run on an
RK3566 (no board on the bench).

What differs from ISP30, and how the crate handles it (`Generation::Isp21`):

- Layouts: `rkisp_isp21_stat_buffer` and `isp21_isp_params_cfg` (no `exposure` block). Bls,
  AWB gain, CCM and CSM structures are the same as ISP30's (`isp21_*`).
- Lens shading: the driver's tables have 8 size and gradient entries per axis and the
  driver has no 16x16 flag (`isp_lsc_config`, ISP30's `sector_16x16`). The crate reads them
  as 8x8 sectors: the 9x9 vertices go in the top-left of the 17-wide table the driver writes.
  Which entries the hardware reads for 8x8 sectors is not in the driver: to confirm.
- Output gamma: 45 samples (`ISP2X_GAMMA_OUT_MAX_SAMPLES`), no `finalx4_dense_en`.
- Zero gains: the driver refuses a parameter buffer with a zero AWB gain
  (`isp_awbgain_config`: "awb gain is zero!") and keeps the previous gains. Both generations
  write a zero gain as 1/256 (ISP30's driver checks the same).
- Statistics: the big raw AE block and histogram (`rawae3`, `rawhist1`) are read as on ISP30,
  at ISP21's offsets in the statistics buffer.
- Device: the node names (`rkisp-isp-subdev`, `rkisp-input-params`, `rkisp-statistics`,
  `rkisp_mainpath`), the pad numbers and the meta formats (`RK1P`, `RK1S`) are the same as on
  ISP30 (`isp_params.c`, `isp_stats.c`, `rkisp.h`, `capture.h`: one driver, `DRIVER_NAME`
  `rkisp`), so `find_isps` and `IspDevice` need no change.

Constants taken from the shared structures, to confirm on the device: `GAIN_ONE` (8
fractional bits), `CCM_ONE` (7), `LSC_ONE` (10 in a 12-bit sample), the lens shading sector
sizes (the sectors cover the frame's Bayer quads, half its size, as on ISP30), the gamma
samples' spacing (`equ_segm` 1, equally spaced), and the AE zone scales `AE_RB_FULL` and
`AE_G_FULL`, which assume ISP30's mean bit layout (`ISP2X_RAWAEBIG_GET_MEAN_*`; not checked
against the ISP21 driver's macros).

The camera pipeline picks the generation from the SoC (written, untested on board):
`styx_rkisp::Isp::detect` reads the root devicetree compatible list
(`/proc/device-tree/compatible`): `rockchip,rk3566` and `rk3568` are ISP21, `rk3588` and
`rk3588s` ISP30, `rv1106` and `rv1103` ISP32, `rk3562` ISP32-lite; anything else (RV1103B's
ISP33, RK3576) is refused rather than guessed. `RkispPipeline` builds that generation's buffer
(`AnyParams`, one buffer reset and rebuilt each frame) and reads its statistics.

### The self path: pyramid levels (written, untested on board)

With `native_pyramid_level` set, `IspSetup::self_path` also links the ISP's source pad to
`rkisp_selfpath` (`SP_VDEV_NAME`, every generation) and opens it as a second NV12 queue at the
level's size. Each frame's self path image is copied into a pooled buffer, its V4L2 buffer
given back at once, and attached to the main frame as a `CompanionKind::Pyramid` companion;
the main frame stays a zero-copy lease. Whether the media core enables the second link from
the same source pad as the vendor driver does at probe is the first thing to check on a board.

## RK3562 and RV1106 (ISP32 and ISP32-lite): written, untested on board

Status: written, untested on board. The buffers are the BSP's `rk-isp32-config.h`, their sizes
and offsets checked against the C compiler's; the builder and the statistics are unit-tested
against fabricated buffers (`crates/rkisp/src/isp32/tests.rs`). Nothing has run on an RV1106 or an
RK3562. The code is `styx_rkisp::isp32`, selected by a `Variant`.

### Generations (from the BSP)

Rockchip's kernel, `drivers/media/platform/rockchip/isp/` in develop-6.1 (develop-5.10 agrees
for the match data):

- RK3562 is the ISP32-lite, `ISP_V32_L` (`common.h:79`): `rk3562_isp_match_data` in `hw.c:922-925`
  (5.10: `hw.c:846-849`), compatible `rockchip,rk3562-rkisp` (`hw.c:980`).
- RV1106 is the full ISP32, `ISP_V32` (`common.h:78`): `rv1106_isp_match_data` in `hw.c:889-892`
  (5.10: `hw.c:824-827`), compatible `rockchip,rv1106-rkisp` (`hw.c:1013`).
- The BSP's Kconfig groups them as "isp32 for rv1106 rk3562" (`Kconfig:39`). RV1103B is ISP33
  (`hw.c:881`) and is not covered here.

The uAPI header `rk-isp32-config.h` is byte-identical in develop-5.10 and develop-6.1. The
`rk-isp2-config.h` differs between them only in API macros and `ISP2X_MESH_BUF_NUM`; the layouts
the ISP32 structures use are identical (a C probe prints the same sizes and offsets for both).

### What differs between the two

| | RV1106 (ISP32) | RK3562 (ISP32-lite) |
| --- | --- | --- |
| Parameter buffer | `isp32_isp_params_cfg`, 11145 bytes | the same |
| Statistics buffer | `rkisp32_isp_stat_buffer`, 13036 bytes | `rkisp32_lite_stat_buffer`, 3788 bytes |
| AE zones (15x15) | `rawae3_0`: packed 4-byte zones, g 12 bits, b and r 10 bits (`isp32_rawae_meas_data`, `rk-isp32-config.h:1352`) | `rawae3`: 6-byte zones of three 16-bit fields (`isp2x_rawae_meas_data`) |
| Big histogram | `rawhist1` (offset 5120) | `rawhist3` (offset 1924); `rawhist1` is masked out (`isp_params_v32.c:4269`, `:4323`) |
| Outputs | mainpath, selfpath, bypasspath, mainpath and bypasspath 4x4 sampling, lumapath, iqtool | mainpath, selfpath, iqtool |

The stream registration is `rkisp_register_stream_v32` (`capture_v32.c:2260-2285`); the path
diagram is at `capture_v32.c:17-25`. The lite's AE and histogram readers are
`rkisp_stats_get_rawae3_meas_lite` and `rkisp_stats_get_rawhst3_meas_lite` (`isp_stats_v32.c`).

### Nodes and formats

- The ISP subdevice is `rkisp-isp-subdev` (`rkisp.c:57`), its pads the ISP30 ones (`rkisp.h:115-119`):
  the source pad carries every path (`rkisp.c:5292`, `capture.c:1910`).
- The parameter node is `rkisp-input-params` (`isp_params.c:22`), format `RK1P`; the statistics
  node is `rkisp-statistics` (`isp_stats.c:21`), format `RK1S` (`isp_params.c:477`,
  `isp_stats.c:300`). The same names and fourccs as ISP30, so the [`device`](#styx-rkisp) layer should open them
  unchanged (untested); the main path is `rkisp_mainpath`.
- The path nodes are `rkisp_selfpath`, `rkisp_bypasspath`, `rkisp_mainpath_4x4sampling`,
  `rkisp_bypasspath_4x4sampling`, `rkisp_lumapath` and `rkisp_iqtool` (`capture.h:46-53`);
  `styx_rkisp::isp32::nodes` and `Variant::output_nodes` list them.

### Pyramid levels (RV1106)

- The selfpath is the second, scaled output (`rkisp_selfpath`, both variants).
- The 4x4 sampling outputs are `rkisp_mainpath_4x4sampling` (MPDS) and
  `rkisp_bypasspath_4x4sampling` (BPDS), full ISP32 only. They are the two sampled levels.
- The BSP has no 8x8 pyramid path. The `RKISP_AIAWB_DS_8X8` in the 6.1 `rk-isp2-config.h` is an
  AI-AWB downsample option, not a pyramid output.
- Opening the selfpath as a second output of `IspDevice` is not implemented: see below.

### Constants that are guesses

The header states none of the fixed-point scales. They are ISP30's (`GAIN_ONE` 256,
`CCM_ONE` 128, `GAMMA_OUT_MAX` 4095, `LSC_ONE` 1024, `AE_RB_FULL` 1023, `AE_G_FULL` 4095), taken
from the same registers' formats, to confirm on a board. The lite's 16-bit zone fields are read
with the same scales. The histogram mode, weights and the 15x15 window are ISP30's. The
driver writes the AWB and CCM fields to the registers as given (`isp_awbgain_config`,
`isp_ccm_config`), so the scales are the registers' own.

- The driver refuses the whole AWB gain block when any gain is zero (`isp_params_v32.c:781-788`,
  "awb gain is zero!"). The builder writes a gain that rounds to zero as 1/256, as the ISP21
  and ISP30 builder does (`isp_params_v3x.c:721` refuses the same way).
- `bound_bit` and `right_bit` share one CCM register and the driver's comments do not say what
  they scale; they are left at zero, as ISP30's are.

### Not done

- Pipeline: `styx_pipeline::rkisp` is ISP30-only; nothing selects `isp32` yet.
- The selfpath as a second output: the ISP's source pad has no `MEDIA_PAD_FL_MULTIPLEX`
  (`rkisp.c:5292`), so the selfpath link would be a second enabled link from the pad the main path
  already uses. Whether the media core accepts that is unverified; needs a board.
- The full ISP32's AF-AE mode (`afaemode_en`), which makes the driver skip the `rawae3` config
  (`isp_params_v32.c:4293`, `:4346`): the builder does not set it.
- Denoise, sharpening and the other modules stay at the driver's defaults, as on ISP30.
